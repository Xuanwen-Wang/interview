# VP 吞吐口径与条件模型

日期：2026-11-15。对应 `web/vp-capacity.js`、`scripts/check_vp_capacity.js` 及正文 `vp-throughput`、第七部分。硬件前提见 [RTL 复核](vp-rtl-depth-20261115.md)；算子实际配方见 [算子与编译器复核](vp-operator-depth-20261115.md)。

## 模型合同

只覆盖连续、满有效组、普通 BF16/FP32 tensor 输入输出。每路 tensor 的格式相同，无广播或缓存复用。每结果计一次 MUL，或配方中有序的 MUL 与 ADD 两次基本运算；不把 PRG、EXP、比较和归约各记成一个等价 FLOP，不宣称融合 FMA。

- 组大小 `q`：pipe 或 FP32 输入为32，否则为64。
- 每个结果组消耗 `streams` 个读包；X/Y 共用读服务，不把它们当作两条独立读口。
- 每个结果组产生 `ceil(q × output_bytes / 128)` 个写载荷。
- 条件结果率 `R = min(q, q / streams, q / write_beats)`。
- 结果率换算：`Gelem/s = R × MHz × VP_count / 1000`。
- 基本运算换算：`TOPS = Gelem/s × ops_per_result / 1000`；所计为浮点算术时，同值可写为 TFLOPS。

计算组、读服务与写服务在这个计算器中按同速归一化：每拍最多推进一个有效计算组，每拍服务一个读包、接受一个写载荷。RTL 的 `core_clk` 与 `vp_clk` 并不由这个模型证明等频。频率默认400MHz是换算条件，4VP是四路都获得所需服务时的条件总和，不是L2带宽保证。

## 与有效字节除法不同的反例

pipe BF16每组32元素、64B有效数据。P2S用strobe屏蔽未用块，不把两个计算组紧凑拼成128B。双tensor输入每组分别读取X/Y；即使有效字节总和只有128B，也不能把两次读服务减为一次。因此条件结果率为16元素/归一化拍，而不是32。

wide BF16输入每组64元素；若输出FP32，一组256B结果需要两次写服务，写侧上界32元素/拍。格式变更会改变读写包合同，不能只引用物理64lane容量。

## 验证及范围

独立检查枚举4096个结果对应的计算组，并逐组数读包和按128B切分写包，验证两种模式、两种输入类型、两种输出类型、单双tensor的16个组合；另核对频率、VP数、基本运算次数换算，以及pipe半有效载荷和错误输入。

这是逻辑分组与服务预算，不模拟RTL时钟、地址仲裁、FIFO延迟、尾块、参数装载、写响应延迟、数值舍入或设备吞吐。正文性能章用单独的包/秒和VP时钟变量说明如何解除同速归一化假设。未执行本轮kernel编译、CycleSim、VCS/RTL或设备实验。
