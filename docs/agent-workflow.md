# 协作与验收

根 [AGENTS.md](../AGENTS.md) 是任务入口；[源码导航](source-navigation.md) 负责找依据，[编写规范](authoring.md) 负责讲清楚。详细规则各维护一份，其他入口用链接引用。

## 开始与并行

1. 读取当前规则和必要的本机配置，核对分支、HEAD 与 `git status --short`。收到新要求时更新本轮约束，不用历史文档覆盖当前用户要求。
2. 明确本次要改的文件和完成条件。只读调查可以并行；多个 agent 不同时改同一文件，综合修改由明确的负责人集成。
3. 工作区已有他人或其他任务改动时，保留原状。需要 worktree 时从明确的基线创建；交付只提交本任务变更。同步回原目录前复查文件是否又有变化。
4. 业务库只作来源。若任务实际需要编译器修复或 kernel 实验，作为对应业务仓库的工作处理，先遵守该库规则，不夹在网页改稿中执行。

## 查代码到写结论

每个重要结论保留一条可追踪链：问题 → 入口 → 关键实现 → 调用与数据合同 → 验证或限制。不要因搜到一个同名文件就认定运行时采用了它。

源码记录至少包括仓库别名、commit、dirty 状态、相对文件及符号、采集日期。依赖树、编译产物与源码树分别确认；Git 不可用时记录相关文件 SHA256，写明 revision unknown。索引中的位置是查找起点，不能把一次审稿的 SHA 当作永远有效的版本。

性能说明同时交代输入 shape/dtype、计时区间、聚合口径和分母。旧日志属于历史测量；纯源码分析、字节建模、CycleSim、VCS、硬件 kernel 与端到端结果分别陈述。

## 三个审查问题

| 审查 | 必须能回答 |
| --- | --- |
| 技术正确性 | 结论由哪份源码、论文或实验支持？公式与 shape 是否相容？不确定项有没有标注？ |
| 初学者可理解性 | 读者在看到新名词、符号和数字前，是否已获得定义？能否沿图说明一次输入到输出？ |
| 视觉可用性 | 对比对象和比例是否明确？连线是否正确且不穿字？手机、放大、动画末帧与打印能否阅读？ |

数学模型的测试不能替代后两项。审稿可以由另一 agent 完成，但负责人仍需查看实际截图与有争议的推导。对可客观检查的性质使用脚本；不要为“看起来更美观”编写只匹配文案的测试。

## 发布前后

1. 执行与改动匹配的检查。发布前必须构建并运行 `scripts/check.py`、`scripts/check_public_artifact.py`；审阅生成的完整 `dist/`，包括所有独立 HTML 中内嵌的数据。
2. Pages 的发布边界是经过检查的 `dist/`；指南源码与规范在 GitHub 仓库公开。`resume/`、本机配置和原始私人资料不提交，仓库根目录不作为 Pages 发布目录；不要通过复制整个仓库解决缺文件问题。`dist/` 存在额外文件时调查来源，不关闭检查或直接忽略错误。
3. GitHub 指南仓库与 Pages 保持公开，简历独立管理。本规范不要求将指南仓库改为 private；沿用用户已有的提交与发布授权，不因简历独立存放而阻止正常源码推送。
4. 只从当前通过检查的提交发布，CI 仅上传 `dist/`。跟踪该提交的 build/deploy 状态；发布完成后再比对线上关键产物与本地构建，并检查实际页面入口。
5. 最终回复区分“本地完成”“已提交”“已推送”“已部署”“线上已核验”。无法执行的部分写明实际原因，不把排队中当作完成。

仅修改规范且生成 HTML 未变化时，不需要重复录制所有动画；要验证文档路径、检查命令和产物一致性。修改构建或检查逻辑时需验证正常案例与应拒绝的反例。

## 持续维护

每次出现需要用户反复纠正的错误，先判断它是一次内容错误还是可复用的约束：前者修正文，后者在对应规范补一条具体要求。新规则注明适用范围和可执行动作；过时条款同步删除，避免把聊天记录逐条堆进 AGENTS.md。
